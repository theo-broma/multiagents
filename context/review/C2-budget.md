**F120** — Multi-account claude quota reading is unreachable: the built-in fallback always calls `read_claude()` with no arguments, dropping the caller's `config_dir`
*Class:* bug
*Severity:* critical
*Where:* `src/multiagents/budget.py:662-664` (`read_provider`'s builtin dispatch: `budget = builtin() if builtin is read_claude else ...`), `src/multiagents/budget.py:395-410` (`read_claude`'s `config_dir` parameter and its own docstring on why it exists), `src/multiagents/defaults/providers/claude.sh:374-382` (the `budget)` action, which unconditionally `exit 64`s "by design ... falls back to its built-in reader")
*Evidence:* reproduction
*Proof:* `tests/test_c2_budget_characterization.py::test_claude_builtin_fallback_ignores_the_callers_config_dir`, `tests/test_c2_budget_characterization.py::test_a_second_named_claude_account_gets_no_builtin_at_all`
*What happens:* `read_claude(fetch, config_dir)` exists specifically so that "with two subscriptions on one machine, reading the default profile for both would report one account's headroom while the work spends the other's" (the function's own docstring) does not happen — it is meant to read `<config_dir>/.claude.json` / `<config_dir>/.credentials.json` instead of `Path.home()`'s copies. But `claude.sh`'s `budget` action is *deliberately* always `exit 64` ("Claude's quota lives in ~/.claude.json ... Parsing that defensively in shell would be worse code in two places, so multiagents falls back to its built-in reader when a script returns 64"), which means **every single real invocation** of `read_provider("claude", ...)` goes through `_from_script` returning `None` and then `budget = builtin() if builtin is read_claude else ...` — called with **zero arguments**. The `config_dir` that `read_provider`/`read_all`'s own caller passed in (in production, always `global_config_dir()` — see `driver.py:889`, `cli.py:1161`, `server.py:971`) is silently discarded for this one branch; `read_claude` falls back to reading `Path.home() / ".claude.json"` and `Path.home() / ".claude" / ".credentials.json"` no matter what was asked for. A grep of the whole `src/multiagents` tree confirms `read_claude(` has no call site anywhere except its own `def` — its `config_dir` parameter is **dead code from every real caller today**. Compounding this: `budget._BUILTIN` is keyed on the literal string `"claude"`, so a second account configured the documented way (`extends: claude` under a different name, e.g. `claude-work`, per `providers.py`'s own inheritance and this suite's `test_load_providers_folds_extends_for_a_second_account`) never matches `builtin is read_claude` at all — it gets neither the real reading nor the home fallback, just a permanent `known=False, source="none", note="no budget action and no built-in reader"`. Either way — same name with a different `config_dir`, or a differently-named sibling — a second claude subscription's actual quota is never read; `choose_provider`'s family/sibling logic (which is otherwise implemented correctly — see the routing tests in this suite) will confidently round-robin work onto it anyway, because "unknown headroom is not no headroom" makes an ever-`known=False` sibling look exactly as usable as a healthy one.
*Disposition:* fix
*Reasoning:* The whole design — `read_claude`'s `config_dir` parameter, the module docstring's extended discussion of why an empty profile directory needs its own reading, this harness's own `claude_profile_dir` helper insisting "you MUST always pass config_dir" — describes a multi-account feature that provably cannot fire from any code path that exists today. Either `read_provider`'s builtin-fallback branch needs to actually pass `config_dir` through (`builtin(config_dir=config_dir) if builtin is read_claude else ...`), or the feature is aspirational and the docstrings should say so; right now the two disagree; and the second, only when the caller is passing whichever CLAUDE_CONFIG_DIR corresponds to the specific `name` being read, which isn't `global_config_dir()` and doesn't obviously exist yet either.

**F121** — `choose_provider` treats "this provider was never read" as usable when it's the preferred slot, but as unusable when it's a fallback — the same missing-entry state means opposite things depending on argument position
*Class:* bug
*Severity:* high
*Where:* `src/multiagents/budget.py:881` (`elif _has_room(budgets.get(preferred), reserve, preferred in reserved): return preferred, "preferred provider has headroom"`), `src/multiagents/budget.py:896-899` (the chain loop's `if budgets.get(name) is not None and _has_room(...)` gate), `src/multiagents/budget.py:756-764` (`_has_room`, which returns `True` unconditionally for `candidate is None`)
*Evidence:* reproduction
*Proof:* `tests/test_c2_budget_characterization.py::test_choose_provider_preferred_missing_from_budgets_entirely_is_still_chosen`, `tests/test_c2_budget_characterization.py::test_choose_provider_fallback_missing_from_budgets_entirely_is_rejected`, `tests/test_c2_budget_characterization.py::test_choose_provider_fallback_with_known_false_reading_is_accepted`
*What happens:* `_has_room(None, ...)` always returns `True` — the module's stated policy is "unknown headroom is not no headroom." For the **preferred** provider, this is reached directly (`_has_room(budgets.get(preferred), ...)`), so `choose_provider("p", {}, [])` returns `("p", "preferred provider has headroom")` even though `budgets` has no entry for `"p"` at all — nothing was ever read, but the returned reason claims headroom was found. For a **chain fallback**, the exact same "absent from `budgets`" state is excluded before `_has_room` is ever consulted: the loop only considers a candidate `if budgets.get(name) is not None`, so a fallback nobody read is reported as `"q (no budget reading)"` and never chosen — a strictly stronger bar than the preferred slot has to clear. A third state — a candidate that WAS read and came back `known=False` (a real `Budget`, just an inconclusive one) — passes the chain's gate fine and is chosen normally, same as a healthy one. So the actual three-way split is: *never read, as preferred* → usable; *never read, as fallback* → rejected; *read but inconclusive, as fallback* → usable. The line the code draws is "is there a dict entry at all," not "is the headroom known," and it draws that line differently depending on which argument slot the provider is sitting in.
*Disposition:* fix
*Reasoning:* Whichever behavior is intended — treating an unread provider as usable, or requiring a reading before diverting work onto it — `choose_provider` should apply it consistently regardless of whether the provider is `preferred` or in `chain`. As written, a caller that forgets to seed `budgets[name]` for a fallback gets an honest-looking refusal ("no budget reading"), while the identical omission for `preferred` is silently treated as full headroom and reported with a reason ("preferred provider has headroom") that is not true — nothing was read.

**F122** — A cache hit mutates the shared cached `Budget` in place and *overwrites* `spent` instead of merging it, while a fresh (uncached) read merges correctly
*Class:* bug
*Severity:* medium
*Where:* `src/multiagents/budget.py:653-658` (cache-hit path: `budget = cached[1]; budget.spent = spent or budget.spent; return budget`), contrast `src/multiagents/budget.py:671-673` (fresh-read path: `if spent: budget.spent = {**budget.spent, **spent}`)
*Evidence:* reproduction
*Proof:* `tests/test_c2_budget_characterization.py::test_cache_hit_overwrites_spent_instead_of_merging_and_mutates_the_cached_object`, `tests/test_c2_budget_characterization.py::test_fresh_read_merges_spent_rather_than_replacing_it`
*What happens:* `read_provider`'s two return paths for `spent` disagree. On a **fresh** read (cache miss or `use_cache=False`), the caller's `spent` dict is merged over whatever the script itself reported: `{**budget.spent, **spent}`. On a **cache hit**, the same information is instead applied as `budget.spent = spent or budget.spent` — a wholesale replacement, not a merge — and `budget` here is not a copy but the literal object sitting in `_cache[name]`. The mutation is therefore permanent: a second caller passing its own `spent` dict on a cache hit silently erases whatever the first caller's `spent` was, for every subsequent cache hit until the entry expires or `invalidate_cache()` runs, not just for its own call. In a system where `read_provider` is called from several places with per-call spend info (`driver.py`, `runner.py`, `watchdog.py`, `server.py`, `cli.py` all pass their own `spend_by_provider`/`spent`), two callers hitting the same 60-second cache window can make each other's accumulated spend disappear from the shared `Budget` they are both reading.
*Disposition:* fix
*Reasoning:* The fresh-read path's merge behavior is very likely the intended one — it's what the `{**budget.spent, **spent}` was clearly written to do — and the cache-hit path should do the same rather than replace-in-place. Returning a copy on cache hit (or applying the same merge onto a copy) would also close the aliasing hazard of handing out `_cache`'s own object to be mutated by any caller that later calls `.spent = ` on it directly.

**F123** — A script's reported `headroom` is accepted with no range validation, so an out-of-range value (e.g. `1.5` or `-0.5`) produces a `Budget` with an internally inverted-looking severity
*Class:* bug
*Severity:* low
*Where:* `src/multiagents/budget.py:630-634` (`_from_script`'s severity derivation: `used = (1 - float(headroom)) * 100`, with no bound on `headroom` itself)
*Evidence:* reproduction
*Proof:* `tests/test_c2_budget_characterization.py::test_read_provider_headroom_above_1_is_accepted_unclamped_and_reads_as_normal`, `tests/test_c2_budget_characterization.py::test_read_provider_headroom_below_0_is_accepted_unclamped_and_reads_as_critical`
*What happens:* A provider script's `budget` action is trusted to report `headroom` as a fraction in `[0.0, 1.0]`, but nothing enforces that. `headroom: 1.5` (more than fully available — meaningless) is silently accepted and derives `severity: "normal"` (`used = -50`, below every threshold). `headroom: -0.5` (already over-drawn) derives `severity: "critical"` only because the arithmetic happens to push `used` past 90, not because anything recognized the value as out of range. Neither case sets a `note` explaining that the input was nonsensical; both look like ordinary, trustworthy readings downstream.
*Disposition:* accept
*Reasoning:* Low severity because it requires a misbehaving or buggy provider script to trigger (the three shipped scripts don't produce this), and the accidental arithmetic happens to land small overshoots on the "reasonable" side anyway (a `headroom` of `1.05` still reads "normal", a `-0.05` still reads "normal" too, and only larger excursions look obviously wrong). Worth a clamp and a note if a fourth provider's script is ever added without review, but not worth changing before then.

**F124** — An empty or field-less script response and a genuine parse failure both produce `known=False, severity="unknown"`, but only the parse failure carries an explanatory note
*Class:* maintainability
*Severity:* low
*Where:* `src/multiagents/budget.py:617-624` (`json.loads(out.strip() or "{}")` treats blank stdout identically to `"{}"`, both falling through with no `note` set, versus the `except json.JSONDecodeError` and non-dict branches just below, which both set one)
*Evidence:* reproduction
*Proof:* `tests/test_c2_budget_characterization.py::test_read_provider_empty_stdout_parses_as_empty_object_not_an_error`, `tests/test_c2_budget_characterization.py::test_read_provider_missing_fields_object_also_has_no_note`
*What happens:* A script that prints nothing at all, and a script that deliberately prints `{}` to say "I have nothing to report," both produce a `Budget` with `known=False` and `note=""` — visually indistinguishable in `to_dict()`/the monitor from each other, and offering no hint that stdout may have been empty by accident (a crashed script that happened to exit 0, a `printf` typo) rather than by design. A genuinely malformed body (`not json at all`, a JSON array) DOES get a note. The three states an operator actually cares about — "script explicitly has nothing to say," "script produced garbage," "script printed nothing, possibly by mistake" — collapse into two distinguishable buckets, with the first and third sharing one.
*Disposition:* accept
*Reasoning:* Cosmetic/debuggability gap rather than a routing hazard — `known=False` is handled the same way regardless of which of these three states produced it, so nothing downstream picks the wrong provider over it. Worth a one-line note ("budget action printed nothing") if this module gets touched for other reasons, not worth its own change.
