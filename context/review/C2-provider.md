# C2 — Provider seam, quota and failover

Findings from building the test harness for this context. See
`tests/support/c2_harness.py` and `tests/test_c2_provider_harness.py`.

**F100** — `budget._cache` is a plain module-level dict keyed only by provider name, so unrelated tests reading the same provider name bleed state through it
*Class:* correctness
*Severity:* high
*Where:* `src/multiagents/budget.py:597` (`_cache` declaration), `src/multiagents/budget.py:648-673` (`read_provider`'s cache read/write)
*Evidence:* reproduction
*Proof:* `tests/test_c2_budget_cache_hazard.py::test_two_unrelated_tests_sharing_a_provider_name_bleed_through_the_cache`
*What happens:* `read_provider(name, provider, executor, config_dir, ...)` caches its result in `_cache[name] = (now, budget)` and, on a cache hit within `_CACHE_TTL` (60s), returns that cached `Budget` without re-running the provider's script — regardless of whether `provider`, `executor`, or `config_dir` differ from the call that populated the cache. The cache key is the bare provider name string, never a tuple that includes `config_dir` or anything else that actually identifies which script produced the value. In the test suite, `tests/conftest.py` already carries three autouse fixtures (`_machine_state_is_disposable`, `_no_catalog_fetch`, `_no_provider_subprocesses`) built specifically to stop one test's state from leaking into another's under `pytest-randomly`'s randomized collection order, but none of them touch `budget._cache`. Two tests that both use the provider name `"claude"` — the obvious name to reach for, since it is the real shipped provider — can therefore have the second one silently receive the first one's cached `Budget` instead of ever invoking its own script, purely as an artifact of which order pytest happened to run them in. The reproduction demonstrates this directly: a "first test" caches `headroom: 0.9` for a script at one `config_dir`, then a "second test" with an entirely different script and `config_dir` (reporting `headroom: 0.1`) asks for the same provider name and gets back `0.9` — its own script is never run.
*Disposition:* fix
*Reasoning:* This is the same class of hazard the three existing `conftest.py` autouse fixtures were written to close, just in the one module they don't reach. A previous attempt at this harness added a fourth autouse fixture (`_reset_budget_cache`) to `conftest.py` to clear `_cache` before every test; that fix was correct in shape but landed in a file this agent's write scope excludes, so it was reverted at the merge gate. The underlying bug is in production code, not test code: `read_provider`'s cache key should include whatever actually varies the answer (at minimum `config_dir`), or the module should expose a narrower reset hook that a conftest fixture — added by an agent with write access to that file — can call safely. Until then, every test that calls `read_provider`/`read_all` with caching enabled (the default) must call `invalidate_cache()` itself on the way in, as `tests/test_c2_provider_harness.py::test_read_provider_caches_until_invalidated` and `tests/test_c2_budget_cache_hazard.py` now both do — which is workable for a handful of proof tests but does not scale to a full characterization suite where every author has to remember it.
